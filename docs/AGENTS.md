# Документація: інструкції для AI

Ці інструкції застосовуються до змін у `docs/`. Спочатку виконуйте кореневий `AGENTS.md`; цей файл лише уточнює роботу з документацією.

## Навігація

1. Для backend-архітектури прочитайте `sdd/architecture/README.md`.
2. Для сталих правил прочитайте `sdd/standards/README.md`; оберіть тільки релевантні правила. Перед створенням або зміною ідентифікатора сутності прочитайте `sdd/standards/identifier-strategy.md`.
3. Для нової feature або міграції прочитайте `sdd/specs/_templates/README.md` і створіть/оновіть feature-специфікацію до коду.
4. Для запуску, конфігурації, міграцій, діагностики або jobs прочитайте `sdd/operations/README.md`.
5. Щоб ознайомитися зі стандартними термінами, що використовуються в проєкті, перегляньте файл `product/glossary.md`.

## Межі виконання для AI

Коли користувач дозволив реалізацію feature, фази, сценарію або впорядкованого набору задач, продовжуйте виконувати всі готові задачі в погоджених межах без окремої команди для кожного task-файла. Дотримуйтеся залежностей і контрольних точок із `sdd/specs/_templates/ai-feature-workflow/`. Зупиняйтеся лише на межі дозволеного scope або за наявності задокументованого blocker-а.

## Правила документації

- Зберігайте документацію як Markdown поруч із кодом і оновлюйте її в тому ж change set, що й поведінку, яку вона описує.
- `architecture/` і `standards/` містять сталі правила; feature-specific рішення належать у `specs/<module>/<NNN>-<feature>/`.
- Одна відповідальність — один документ. Не створюйте порожні, дублюючі або монолітні файли.
- API-контракти зберігайте в `contracts/` і дотримуйтеся `sdd/contracts/README.md`.
- Для специфікації та реалізації feature використовуйте пов'язані SDD-шаблони, правила тестування й AI workflow; не дублюйте їхні інструкції тут.
- Перевіряйте відносні Markdown-посилання після переміщення або перейменування файлів.
