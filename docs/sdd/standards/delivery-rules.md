# Правила постачання

## SDD flow

1. Визначте мету, scope, бізнес-правила й acceptance-сценарії зі сталими ID `R-*` і `SC-*`.
2. Усуньте неоднозначність прикладів, потім погодьте design, data model, ризики й contracts лише там, де для них є зміст.
3. У traceability matrix зіставте кожен сценарій із технічними задачами та рівнем тестування. Використовуйте `TS-*` для задач реалізації, а `EN-*` — для спільних технічних передумов.
4. Реалізуйте готові задачі сценарій за сценарієм. Усередині кожного тестованого технічного slice застосовуйте Red → Green → Refactor.
5. Перевірте кожен завершений сценарій, а потім запустіть релевантний regression-набір.
6. Оновіть специфікацію доказами, відхиленнями й залишковими ризиками.

## Гранулярність документації

- Одна feature має один orchestration `README.md`.
- Документ відповідає за одну тему; не створюйте порожні або дублюючі файли.
- Acceptance-сценарії описують зовнішньо спостережувану поведінку без деталей реалізації.
- Design-документи залишаються джерелом технічних меж і рішень.
- `traceability.md` пов'язує сценарії, технічні задачі й докази, не дублюючи їхній детальний зміст.
- ADR потрібен лише для сталої архітектурної зміни; звичайні use-case рішення належать у feature design.
- Feature-специфікації посилаються на `standards/`; не копіюйте сталі правила backend, API, безпеки або тестування.

## Definition of done

Кожен сценарій у scope реалізовано або явно відкладено, усі необхідні технічні задачі завершено, а автоматизовані чи задокументовані ручні докази успішні. Контракти й реалізація узгоджені. Релевантні restore/build/test-перевірки виконано або причину їх відсутності зафіксовано. Delivery report містить змінені файли, докази перевірки, неперевірену роботу й залишкові ризики.

Перед позначенням task як виконаного виконайте self-review: звірте scope зі специфікацією, межі відповідальностей файлів із `backend-rules.md`, стиль із сусіднім кодом і точні команди перевірки. Не звітуйте про завершення фази або task за наявності незавершеної залежної роботи.
