# Правила постачання

## Порядок SDD

1. Визначте мету, обсяг, бізнес-правила й сценарії приймання зі сталими ID `R-*` і `SC-*`.
2. Усуньте неоднозначність прикладів, потім погодьте проєктне рішення, модель даних, ризики й контракти лише там, де для них є зміст.
3. У матриці простежуваності зіставте кожен сценарій із технічними задачами та рівнем тестування. Використовуйте `TS-*` для задач реалізації, а `EN-*` — для спільних технічних передумов.
4. Реалізуйте готові задачі сценарій за сценарієм. Усередині кожного тестованого технічного зрізу застосовуйте Red → Green → Refactor.
5. Перевірте кожен завершений сценарій, а потім запустіть відповідний набір регресійних тестів.
6. Оновіть специфікацію доказами, відхиленнями й залишковими ризиками.
7. Після реалізації нової фічі додайте опис поточної будови до [карти фіч](../features/README.md) та її індексу; при зміні наявної фічі звірте й за потреби оновіть опис у тій самій зміні.

## Гранулярність документації

- Одна SDD-специфікація фічі має один координаційний `README.md`; короткий опис фактичної реалізації зберігається окремо в `features/`.
- Документ відповідає за одну тему; не створюйте порожні або дублюючі файли.
- Сценарії приймання описують зовнішньо спостережувану поведінку без деталей реалізації.
- Проєктні документи залишаються джерелом технічних меж і рішень.
- `traceability.md` пов'язує сценарії, технічні задачі й докази, не дублюючи їхній детальний зміст.
- ADR потрібен лише для сталої архітектурної зміни; звичайні рішення сценарію належать до проєктного рішення фічі.
- Специфікації фіч посилаються на `standards/`; не копіюйте сталі правила backend, API, безпеки або тестування.

## Критерії завершення

Кожен сценарій в обсязі реалізовано або явно відкладено, усі необхідні технічні задачі завершено, а автоматизовані чи задокументовані ручні докази успішні. Контракти й реалізація узгоджені. Відповідні перевірки відновлення залежностей, збірки й тестів виконано або причину їх відсутності зафіксовано. Звіт про поставку містить змінені файли, докази перевірки, неперевірену роботу й залишкові ризики.

Перед позначенням завдання як виконаного проведіть самоперевірку: звірте обсяг зі специфікацією, межі відповідальностей файлів із `backend-rules.md`, стиль із сусіднім кодом і точні команди перевірки. Не звітуйте про завершення фази або завдання за наявності незавершеної залежної роботи.
