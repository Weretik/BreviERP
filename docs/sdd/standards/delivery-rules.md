# Delivery rules

## SDD flow

1. Створіть feature-специфікацію з метою, межами, сценаріями, контрактами, ризиками та критеріями приймання.
2. Додайте design, data model, contracts і quality checklist лише коли для них є зміст.
3. Розділяйте реалізацію на нумеровані фази й атомарні задачі, якщо їх можна незалежно рев’ювати або постачати.
4. Реалізуйте лише погоджену роботу в межах scope.
5. Оновіть специфікацію доказами перевірки та залишковими ризиками.

## Гранулярність документації

- Одна feature має один orchestration `README.md`.
- Документ створюється для однієї відповідальності; не створюйте порожні або дублюючі файли.
- ADR потрібен лише для сталої архітектурної зміни; звичайні use-case рішення належать у feature design.
- Feature-специфікації посилаються на `standards/`, а не копіюють сталі правила backend, API, безпеки або тестування.

## Definition of done

Критерії приймання закриті, релевантні тести оновлені, restore/build/test були виконані або причина зафіксована. Delivery report містить змінені файли, докази перевірки, те що не вдалося перевірити, і залишкові ризики.

Перед позначенням task як виконаного виконайте self-review: звірте scope зі специфікацією, межі відповідальностей файлів із `backend-rules.md`, стиль із сусіднім кодом і точні команди перевірки. Не звітуйте про завершення фази або task за наявності незавершеної залежної роботи.
