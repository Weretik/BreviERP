# API-контракти

`docs/sdd/contracts/` — канонічне, версіоноване джерело машиночитаних контрактів публічного API.

## Структура

```text
docs/sdd/contracts/
├── openapi.yaml                         # агрегована точка входу для всіх публічних API
└── <module>/
    └── <feature>.openapi.yaml           # контракт, яким володіє одна функціональність
```

`openapi.yaml` є точкою входу для Swagger UI, генерації клієнтів фронтенду та контрактних тестів. Він посилається на контракти модулів через `$ref`; не дублюйте операції або схеми в агрегованому файлі.

## Поточна передача frontend-команді

- [Інструкція інтеграції frontend](frontend-integration.md) описує authentication, CSRF, paging, errors і поточне contract coverage.
- [Агрегований контракт OpenAPI 3.1](openapi.yaml) охоплює API, для яких уже створено й перевірено versioned contract.
- Контракти модулів: [Catalog products](catalog/product-catalog.openapi.yaml).

OpenAPI-файли описують контракт фактичного коду. Вони не надають endpoint публічного доступу: авторизаційні атрибути й host fallback policy залишаються authoritative.

Кожна SDD-специфікація функціональності містить `contracts/api-contract.md` для опису рішень, призначених для людей: меж, споживачів, сумісності, безпеки, помилок, ідемпотентності та розгортання. Для нової або зміненої HTTP-поведінки, коли це практично, погодьте ці рішення й створіть або оновіть машиночитаний контракт до transport-реалізації. На основі погодженого контракту додайте сфокусовані contract/API Red-тести, а потім реалізуйте transport. Документ feature має посилатися на `docs/sdd/contracts/<module>/<feature>.openapi.yaml`, а агрегований `openapi.yaml` потрібно оновити в межах тієї самої зміни.

Не створюйте публічний OpenAPI-документ для змін, що використовуються лише всередині системи. Перш ніж додати HTTP-контракт, погодьте маршрут, метод, ідентифікатор операції, DTO, приклади, помилки, безпеку, ідемпотентність для записів із побічними ефектами та шлях міграції для несумісних змін.
