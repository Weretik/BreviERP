# Module schemas

**Status:** implementation

This change separates persistent data of the modular monolith into PostgreSQL schemas without losing existing data.

## Ownership

| Schema | Owner | Tables |
| --- | --- | --- |
| `catalog` | Catalog | products, catalog categories, media and product details |
| `reference` | Reference | additional references, fabrics, garment accessories, parts, operations, suppliers and reference product categories |
| `identity` | Identity | ASP.NET Identity tables and refresh sessions |
| `accounting` | Accounting | transaction categories |
| `public` | PostgreSQL / shared infrastructure | existing `__EFMigrationsHistory`; no module-owned tables after rollout |

`public.ProductCategories` is a legacy table with no current Reference entity mapping. The active Catalog model owns `catalog.ProductCategories`; Accounting must not reuse either table and stores its aggregate as `accounting.TransactionCategories`. If the legacy table exists, the Reference migration deletes it; `DROP TABLE IF EXISTS` also supports databases where it was already removed.

## Safety

- Existing Reference and Identity tables are moved with PostgreSQL schema moves generated by EF migration; this preserves rows, indexes and constraints.
- The pre-existing Accounting initial migration is not applicable because it attempts to create `public.ProductCategories`, already owned by Reference. It is replaced before any Accounting migration is applied.
- The common migration-history table remains in `public`; moving it would make each DbContext lose its applied-migration baseline.
- The Reference migration's deletion of confirmed-obsolete `public.ProductCategories` is irreversible. Its `Down` method reverses only schema moves for active Reference tables.
