## Input and source boundary

The frozen input JSON (schemaVersion1) contains datasetId, databaseFile, databaseSha256, manifestFile, manifestSha256 and optional optionsFile/optionsSha256 and blobs(sourceFileId/file/sha256/length). Referenced native/options/blob files resolve only below an explicitly supplied sourceRoot; relative traversal, absolute filenames, URLs and symlink/reparse escapes are rejected. Each file is bounded to64MiB, verified against its SHA256 before parsing, and parsed strictly. Native D1 database.json is table-name -> {columns,rows}; native manifest.json supplies extraction flags, expected counts, per-table status/truncation/issues. All reported selected table lengths must match the frozen native counts. Source hashes prove integrity, never completeness. An unreadable top-level artifact stops without partial success and without raw error contents.

Only the12 CRM history tables are normalized: counterparties, quotes, quote_versions, quote_items, quote_change_log, quote_transfers, quote_email_sends, quote_ppe_price_overrides, custom_sewing_drafts, custom_sewing_versions, custom_sewing_files and introduction_saved_templates. Auth/OAuth/session/finance payloads and configuration/index tables are not staged. Counterparty bank/finance fields never enter normalized metadata. Snapshot/payload cells are checked without repair; truncation/invalid JSON is quarantined. Exact parents, versions/current version and required graph members are validated. Metadata-only files are not treated as available bytes. Optional exact-source-file blob entries must match actual bounded bytes, frozen hash and native declared size; missing/mismatched blobs remain explicit gaps. Historical sends remain inert.

ControlSha256 seals the actual freeze document (including blob/options hashes); OptionsSha256 records the verified options file. The optional options document has stagingDatasetId (required for a nonempty same-dataset previous ledger), ownerMappings(hash-of-normalized-source-email -> positive existing Identity ID), exactIdentityMappings(hash-of-exact-external-source/type/id tuple -> target public UUID), previousStaging(entity/sourceId/payloadSha256), scopeApprovalReference and retentionPolicyReference. No names or email similarity is used, no identity is created, no existing target ID is inferred. These are operator-reviewed inputs; TS-014 must verify targets against actual stores before any future write. For counterparty roots lacking a source owner, OwnerKeys contains SHA256('counterparty:'+opaque sourceId), requiring an explicit reviewed custodian mapping. Email owner keys use SHA256 of trimmed lowercase email; no email is printed. Missing maps/approvals are visible blockers. The current implementation always returns importAuthorized=false and databaseWrites=0.

## Planning and accounting

Normalized contracts are in Crm.Application/Imports/History/Contracts. A staged row contains only an opaque source ID, payload hash, explicit role/kind, hashed owner/external identity keys, dependency IDs and safe issue codes. Known source IDs use bounded ASCII identifier syntax; invalid values must not leak into reports. The planner belongs to Application, file/hash/native-format adapters to Infrastructure. No CatalogImport dependency is introduced: its validate mode already opens a database transaction.

Each selected source row has exactly one classification: wouldImport, alreadyStaged, alreadyMapped, needsReview, excluded or invalid. SourceRows equals their sum. wouldImport is a candidate only, not an inserted row. Same entity/sourceId/hash from a prior staging ledger or duplicate input is alreadyStaged, not a claim of a target import. A changed hash for the same key is a review conflict; conflicting duplicates block that graph. Exact supplied external identity maps are used before candidates; divergent maps conflict. Only explicit CLIENT membership qualifies as a customer (including dual roles); supplier/finance-only records are excluded, unknown roles/kinds unresolved. Missing/invalid dependencies propagate review to affected graphs. Unknown legacy individual content stays review-only, never becomes a Product/PPE guess.

Reports contain aggregate metadata, opaque key hashes, payload hashes and reason codes; no customer names, phone/address, actor emails, raw JSON, tokens or finance values. The separate staging ledger contains only validated opaque source IDs/hashes and must stay outside Git with source files. Reports and ledger must never overwrite any input and are written only to an explicitly selected restricted output path. No automatic approval or target activation follows a successful run.
