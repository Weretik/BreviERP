## Implementation and invariants

Domain CustomSewing/Attachments stores typed long file metadata and draft/version link identities with separate opaque public IDs. Each upload uses a durable known object ID, actor/requestId payload hash and Reserved/Uploaded/Deleting/Expired state. Actual PDF/JPEG/PNG signatures, inclusive 20 MiB, hash and length are validated; Domain and Application share the same byte cap. Root quota is 30 retained/reserved files and serializes competing uploads.

Upload performs scope validation and bounded input read, a short Quote→Draft reservation transaction, known-ID byte write/readback outside that transaction, then short scoped completion. Same request/payload recovers the same object; changed payload conflicts. Deterministic `.pending-{fileId}` paths permit known-object crash cleanup. Expiry is checked under filesystem lock immediately before atomic rename, preventing a delayed writer from resurrecting cleaned bytes. Arbitrary posted owner/path/URL is not accepted.

Explicit finalize uses requestId/expectedRevision, verifies actual Uploaded bytes, replaces normalized draft links and increments root revision in the existing mutation journal transaction. ShowInQuote and Production are independent. Saving a custom version pins a pure relational snapshot of file metadata/flags after version insertion and before the root pointer changes; same-draft restrictive composite FKs and append-only trigger preserve history. Current file edits never rewrite a quoted V1.

Reading rechecks current actor scope and actual bytes/hash; content requires finalized current links or an exact immutable version. A supplied quote context grants only custom versions actually pinned in that currently accessible quote, including copy/transfer history. It never grants access to other versions of the source draft. Public/production projection filters run on the server and contain no private cost or physical path. Content responses are private/no-store/nosniff with GUID-based download names; pending files are 404.

Cleanup is an explicit internal bounded service. It claims only expired uploads with no current/history links, rechecks references in a fresh statement under the file lock before changing state, then deletes only that known object's committed/pending paths outside the transaction. A retryable Deleting state and filesystem lock make recovery idempotent. No root lock is acquired after a file lock. Finalize/cleanup races cannot leave retained files Deleting; referenced historical bytes are never selected for cleanup.

Temporary lifetime defaults to 24 hours, configurable within 1 minute–7 days. This is not a historical retention duration; EN-006 still owns that policy. No cleanup worker is enabled.
