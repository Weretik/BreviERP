# Crm data model by rollout slice

**Current state (2026-10-29):** client, P2/P3 quote/history, TS-006 private custom draft/version/calculation, TS-008 configuration-template, TS-007 file/link/history and TS-009 issuer/template/number tables are implemented locally. TS-009 PostgreSQL integration is still pending; ready/PDF, delivery and import tables remain target design. Earlier custom migrations were verified only on disposable local databases; no working-database application is claimed. Crm owns schema `crm` in the existing PostgreSQL database; [actual database map](../../../architecture/data-model/crm.md) lists implemented constraints. Follow the module schema and identifier rules; operational data stays in PostgreSQL.

## Identifiers and references

Ordinary centrally created business records use **typed long IDs** in Domain and numeric relational keys; separate unique Guid `PublicId` values identify public resources. Child/join keys may be composite where lifecycle permits. Typed Identity actor reference wraps its existing int user ID; Catalog/Reference refs preserve the existing owner's scalar/typed identity behind Application ports. Human document number is a separate immutable string. Source text/UUID IDs are retained in external mapping rows, not reused as database primary keys or blindly cast to another module ID. No cross-module EF navigation or cascade delete.

The table list describes ownership, not permission to create every table in the first migration. Each slice introduces only required mapping/indexes and tests. Flatten/split value-object columns deliberately in EF configurations; do not expose internal storage JSON as an untyped client write schema.

P3 implemented storage: `QuoteLifecycleEvents` is one append-only audit table for version and ownership/archive actions, with Guid event PublicId as primary key, typed QuoteId/CrmUserId references, unique (QuoteId,Revision), action, version number, previous/current owner, reason and UTC time. Event identity follows the event Guid rule; no redundant central sequence is needed. A PostgreSQL trigger rejects UPDATE/DELETE. Quote roots add nullable SourceQuotePublicId/SourceVersionPublicId provenance and an IssuedVersionId pointer with a restrictive same-quote composite FK. Copy has fresh logical item/variant IDs, no issued pointer/number/delivery state, and exact saved monetary provenance. No Identity FK crosses the module boundary.

## Invariants and data precision

- Required FKs within `crm` are restrictive; historical records cannot cascade away. Root current/issued pointers must reference its own version, tested in persistence and application invariants. Parent versions cannot reference another quote or cycle.
- Item/variant order is unique within its immutable parent. A draft update inserts a whole validated version and then atomically moves the current pointer; partial children are never visible.
- PostgreSQL numeric columns, C# decimal and explicit currency. Implemented quote tier money is numeric(20,2); custom final prices are checked against that exact range. Private custom cost/source breakdowns use decimal in typed JSONB without intermediate rounding. Planned normalized norms/minutes use numeric(20,6), rates numeric(20,8); only introduce these columns when their table is implemented. Store computation evidence and final displayed two-decimal amount separately where required. No binary floats or extra VAT/round at presentation.
- Nonnegative norms are insufficient for required material/operation selections: calculation requires positive quantities; optional inactive/hidden tier is nullable/unavailable, never zero as an error sentinel. Validate overflow before persistence. Imported malformed values remain in staging.
- UTC instants in `timestamptz`; display dates using configured Europe/Kiev zone. Preserve source raw timestamp and conversion provenance for ambiguous old dates; never guess a missing send time.
- Enforce unique PublicIds, source keys, quote number, version number, request keys and outbox delivery keys. Index quote owner/archive/updatedAt+ID, customer/number/status filters, client owner/name search, version FK and pending delivery lease. Use bounded SQL projections, stable tie-breaker and tested page/count filters; do not index every JSON field in advance.

## Snapshot schema and compatibility

Snapshot schema v1 holds recipient and issuer snapshots; logical items/variants with visible flags; source product/article/custom IDs and version refs; input lines and revisions; formula/settings IDs; cost breakdown and tiers; override provenance; public text/media; actor/time. Typed immutable records serialize to versioned payloads; normalized children support query/integrity. Store payload hash where useful for reconciliation. An explicit read adapter supports older snapshot schema; no destructive rewrite of issued content.

Changing customer/issuer/master data does not update snapshots. Repricing inserts a new version. Migration maps source keys and preserves raw source payload in restricted staging with completeness status; unresolved history cannot be marked as newly issued.

## TS-006 selected storage design — 2026-10-28

Private custom roots and immutable versions use typed long CustomDraftId/CustomVersionId keys and separate unique Guid PublicIds. Typed configuration and calculation-basis records are serialized into versioned private JSONB columns; they are not arbitrary client JSON. Root scalar name/type/season support bounded SQL projection. Same-draft composite FKs protect current/parent version pointers; append-only version triggers preserve historical configuration and costs. Calculation bases and mutation journals use long relational keys with actor/root/request scope and unique opaque Guid tokens. Quotes retain a numeric restrictive FK to the selected CustomVersionId and a typed saved custom snapshot. No cross-module EF FK or navigation. Additive migration runs through the existing Crm Host.Seed path before deployment; rollback must retain history once referenced, never drop live custom versions. Verification uses disposable PostgreSQL only.

## TS-008 selected storage design — 2026-10-28

Configuration templates use typed long CustomTemplateId and CustomTemplateVersionId keys because there is one relational writer/database; separate Guid PublicIds form the API identity. Version.TemplateId is a restrictive numeric FK. Version number is unique per root; root revision is a concurrency token. CustomSewingTemplateVersions stores immutable introduction plus typed price-free selections/norms in JSONB. PostgreSQL rejects history UPDATE/DELETE. The technical long-key mutation journal retains actor/operation/requestId, payload hash and exact response in the same transaction.

Applying a selected immutable version creates a new private custom root, preserving typed nullable TemplateOrigin JSONB (source public IDs and introduction snapshot). It never copies price basis, private note or artwork links. Future template revision/archive cannot alter this snapshot. No cross-module FK or template-based current supplier price is introduced. AddCustomSewingTemplates is additive; deploy migration before activating API. Down is for an unused disposable/undeployed schema only: it drops template history and origin, so retain data and roll back application code when templates have been used. No working-database migration or deletion is authorized by this change.

## TS-007 selected storage design — 2026-10-28

CustomPrivateFiles uses typed long CustomFileId because file metadata has one relational writer/database; a separate opaque Guid PublicId is also the reserved private byte-object identity. The metadata row records typed draft/actor references, requestId/payload hash, verified MIME/length/SHA-256 and Reserved/Uploaded/Deleting/Expired state. Actor/requestId is unique; root/state and state/expiry indexes support bounded quota/maintenance. State is a concurrency token. No source URL or caller-controlled physical path is stored as file availability.

CustomDraftAttachments is keyed by typed (DraftId,FileId), with independent ShowInQuote/Production flags. Its same-draft restrictive composite FK prevents foreign-root linkage. CustomVersionAttachments is keyed by typed (VersionId,FileId), with same-draft restrictive version/file FKs and frozen flags/content metadata; database trigger rejects history UPDATE/DELETE. Saving a version copies these rows in the existing custom mutation transaction. Quotes already pin a numeric custom-version FK, so later draft file changes cannot rewrite a quoted file set.

Byte IO is outside upload reservation/completion transactions. Known reserved IDs and deterministic pending paths permit crash cleanup; filesystem expiration validation prevents a delayed write after an expired reservation is cleaned. Finalization/verification performs bounded local reads before accepting links. Cleanup is an explicit bounded service, never an enabled historical deletion job: claim only expired uploads with no current/historical references, delete known temporary bytes, retain a tombstone. Configurable temporary lifetime defaults to 24 hours; historical retention policy remains EN-006.

Migration AddCustomPrivateFileLifecycle is additive and precedes file API activation. Down drops file metadata/version references, so it is only for unused disposable/undeployed data; after use retain metadata/history/bytes and roll back application code. The frontend FE-006 snapshot remains pinned to the preceding custom contract; file operations are a separate FE-007 handoff.
