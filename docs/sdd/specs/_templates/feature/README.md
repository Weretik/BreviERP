# SDD-шаблон backend-функціональності

Використовуйте цей шаблон для нової бізнес-можливості, CRUD-ресурсу або групи backend-endpoint-ів. Він створює один батьківський SDD і окремий SDD-документ для кожної фази реалізації.

## Скопіюйте цю структуру

```text
docs/sdd/specs/<module>/<feature-slug>/
├── README.md                       скопіювати template-feature.md
├── contracts/
│   └── api-contract.md             копіювати, коли є frontend або зовнішній споживач
└── phases/
    ├── 01-domain.md
    ├── 02-infrastructure.md
    ├── 03-application.md
    ├── 04-api.md
    ├── 05-swagger-manual-test.md
    ├── 06-frontend-handoff.md
    └── 99-custom-phase.md          лише для додаткової незалежної фази
```

## Залежності фаз

```text
01 Domain
   ↓
02 Infrastructure ───┐
                     ├──→ 03 Application → 04 API → 05 Swagger → 06 Передача frontend
API contract ────────┘
```

API-контракт можна підготувати до реалізації та уточнювати впродовж фаз 03 і 04. Не створюйте порожні файли фаз: копіюйте лише застосовні фази, але зафіксуйте в батьківському README, чому пропущена фаза не потрібна.

## Розподіл відповідальності

- README описує мету функціональності, межі, сценарії, сумісність, власника та план фаз.
- `contracts` містить лише API-факти для споживача.
- `phases` містить рішення реалізації, план файлів, критерії приймання та перевірку для відповідної фази.
- Не розміщуйте нотатки реалізації в API-контракті та повний опис frontend-payload у документі фази handler-а.
