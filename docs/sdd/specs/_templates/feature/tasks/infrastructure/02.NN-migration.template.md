## Робота

- [ ] TNN1 Створити migration CLI-командою, а не вручну: `dotnet ef migrations add <Name> --project <Infrastructure.csproj> --startup-project <Api.csproj> --context <DbContext>`; не редагувати застосовані migrations.
- [ ] TNN2 Переглянути згенеровані operations/SQL: data loss, locks, default values, backfill і порядок змін. Ручна зміна нової migration допустима лише для погодженого випадку, який generator не може виразити коректно.
- [ ] TNN3 Застосувати migration CLI-командою до порожньої тестової БД: `dotnet ef database update --project <Infrastructure.csproj> --startup-project <Api.csproj> --context <DbContext>`; перевірити schema, indexes і constraints.
- [ ] TNN4 За наявності команди в установленій версії EF Core виконати `dotnet ef migrations has-pending-model-changes --project <Infrastructure.csproj> --startup-project <Api.csproj> --context <DbContext>`.
- [ ] TNN5 Для ризикованої зміни згенерувати й перевірити deployment SQL через `dotnet ef migrations script --idempotent --project <Infrastructure.csproj> --startup-project <Api.csproj> --context <DbContext> -o <migration.sql>`; зафіксувати rollout/rollback або expand-contract plan у `<посилання на design/operations>`.

## Checkpoint

Migration згенерована й перевірена CLI-командами; ризики production rollout і відновлення даних відомі.
