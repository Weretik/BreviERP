# Поступова міграція до scenario-first SDD

Не переписуйте всі історичні документи feature одночасно. Мігруйте наявну feature, коли змінюється її поведінка або користувач явно просить повну міграцію специфікації.

## Feature з новою або зміненою поведінкою

1. Збережіть наявні task IDs та історію verification.
2. Призначте ID `R-*` і `SC-*` поведінці, що змінюється. Незмінені сценарії можна отримати ID, коли вони потрібні для залежностей, без переписування їх формулювань.
3. Додайте `traceability.md` з усіма зміненими сценаріями та наявними сценаріями, потрібними для пояснення regression-ризику.
4. Створюйте orchestration-файли `SC-*` лише для зміненого scope.
5. Новим технічним задачам призначайте ID `TS-*`, а спільним передумовам — `EN-*`.
6. Застосовуйте Red → Green → Refactor до нової поведінки та фіксуйте докази.
7. Зберігайте старі завершені файли фаз як історію; не перетворюйте їх checkbox IDs, якщо користувач не попросив повну міграцію.

## Feature, реалізація якої вже триває

Завершіть активні задачі старого формату без перенумерації та знецінення їхніх доказів. Застосуйте новий test-first protocol до решти нової поведінки, якщо це не суперечить уже прийнятій задачі. Додайте scenario IDs і traceability на наступній безпечній контрольній точці специфікації.

## Повна міграція

Для повної міграції, дозволеної користувачем, зіставте кожен поточний acceptance-сценарій із `SC-*`, створіть повну traceability matrix і перетворіть на задачі `TS-*`/`EN-*` лише незавершену роботу. Збережіть завершені legacy task-файли як пов'язану історію або архівуйте їх окремою перевіреною зміною.

## Контрольна точка міграції

Змінена поведінка має сталі scenario IDs, нова робота простежується, наявні докази збережено, а міграція непомітно не розширює scope.
