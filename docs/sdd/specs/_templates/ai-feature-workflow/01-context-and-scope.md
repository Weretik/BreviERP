# Контекст, scope і вибір задач

## Визначте дозволений scope

Запит користувача може дозволяти всю feature, фазу, один чи кілька сценаріїв `SC-*` або названі задачі `TS-*`/`EN-*`. Використовуйте найширший scope, який однозначно дозволено запитом. Не звужуйте дозвіл на всю feature до одного файла й не розширюйте запит на конкретну задачу до всієї feature.

У дозволеному scope не потрібна окрема інструкція, щоб відкрити й виконати наступний готовий task-файл.

## Прочитайте до внесення змін

1. Знайдіть усі застосовні `AGENTS.md` від кореня репозиторію до кожної запланованої зміни.
2. Прочитайте `README.md` feature, `requirements/`, `traceability.md`, `tasks/README.md`, вибрані task-файли та релевантні design, data-model, contract і checklist-документи.
3. Для HTTP- або integration-поведінки прочитайте зрозумілий людині контракт і відповідний версійований OpenAPI-файл.
4. Прочитайте лише релевантні документи architecture і standards, включно з `docs/sdd/standards/testing-rules.md`.
5. Перевірте наявні код, тести, команди й конфігурацію, потрібні для підтвердження готовності наступної задачі.

## Виберіть наступну задачу

Задача готова, якщо її залежності завершені, покриті сценарії однозначні, шляхи й checkpoint конкретні, а потрібний рівень тестування можна виконати або для нього є обґрунтований задокументований виняток.

У межах сценарію надавайте перевагу такому порядку:

1. спільні передумови `EN-*`;
2. поведінка внутрішнього шару `TS-*`, потрібна зовнішнім шарам;
3. Application-оркестрація;
4. persistence або зовнішні adapters;
5. API-контракт і transport-поведінка;
6. acceptance-перевірка сценарію та regression.

Цей порядок залежностей не вимагає завершувати всі задачі одного шару для всієї feature.

## Коли зупинитися

Зупиніться лише коли дозволений scope завершено або подальша робота потребує невирішеного product-рішення, невдалої передумови, зовнішнього дозволу, руйнівної дії поза дозволеним scope чи іншого конкретного blocker-а. Якщо бракує product-поведінки, запишіть `[NEEDS CLARIFICATION: <запитання>]` у відповідному документі. Не вигадуйте правило, endpoint, DTO field, роль, schema або requirement.
