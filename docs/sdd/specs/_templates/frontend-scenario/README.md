# SDD-інструкція для сценарію frontend

Ця інструкція допомагає підготувати **handoff-сценарій адміністративного frontend** на основі прийнятої backend feature. Результат описує екрани, блоки, кроки та видимі стани користувача, а також відповідність його дій API. Це документ для реалізації frontend в окремому проєкті; він не є завданням змінювати frontend-код у цьому репозиторії.

Зразок результату: [адміністративний сценарій товару](../../../frontend-scenario/catalog/001-product-page/admin-product-scenario.md). Використовуйте його як приклад рівня деталізації, а не як набір правил для іншої feature.

## Коли застосовувати

- Є вимоги feature та реалізований або погоджений HTTP-контракт, і треба передати AI зрозумілий сценарій для створення frontend.
- Потрібно описати, що користувач робить у списку, формі, перегляді та інших екранах, від яких даних залежать дії й як показувати результати та помилки.
- Існує кілька режимів, типів сутності або залежних довідників, для яких звичайного OpenAPI недостатньо, щоб визначити поведінку екрана.

## Джерела й межі

1. Прочитайте `README.md` feature, її `requirements/`, `contracts/`, релевантний design і наявний [OpenAPI](../../../contracts/README.md). Перевірте фактичний delivery/status: запланований endpoint не називайте доступним без підтвердження. Знайдіть контракти довідників, медіа та інших залежностей форми.
2. Бізнес-правила та scope беріть із вимог feature. Точні маршрути, DTO, enum, query-параметри, статуси й формат помилок — з versioned OpenAPI. Не переписуйте схеми в сценарій. Якщо джерела суперечать одне одному, зафіксуйте розбіжність; не створюйте новий HTTP-контракт у frontend-сценарії.
3. Розрізняйте встановлене правило й запропоноване UX-рішення. Наприклад, порядок логічних блоків можна запропонувати для зрозумілого потоку, але не називати його вже погодженим дизайном. Невідомі бізнес-рішення позначайте `[NEEDS CLARIFICATION]` із конкретним питанням.
4. Не додавайте поза scope публічні сторінки, SEO, нові endpoint-и, ролі, workflow-статуси, обчислення або валідаційні правила, яких немає в джерелах. Не копіюйте frontend-технології чи візуальну систему з іншої feature.

## Що створити

Скопіюйте [scenario.template.md](scenario.template.md) до `docs/sdd/frontend-scenario/<module>/<NNN>-<feature>/<actor>-<entity>-scenario.md`. Каталоги `<module>` й `<NNN>-<feature>` повторюють ідентифікатори feature з `docs/sdd/specs/`, але сценарії зберігаються окремо від backend-специфікацій. Заповніть лише застосовні розділи, видаліть підказки й порожні секції. Додайте посилання в `README.md` feature та індекс модуля `docs/sdd/frontend-scenario/<module>/README.md`. Один сценарій повинен мати одну аудиторію і зрозумілий scope; окремі публічний та адміністративний потоки описуйте окремо, коли вони обидва потрібні.

У сценарії мають бути:

- карта екранів і дій актора;
- блоки кожного екрана та послідовність створення/зміни;
- умовні блоки й залежності від типу, довідника або стану;
- джерело даних для вибору та відображення;
- матриця дій і API, включно з переходом від read DTO до write request там, де вони різні;
- стани завантаження, порожніх даних, успіху, validation/conflict/not-found/network помилок за контрактом;
- короткі перевірювані acceptance-сценарії та посилання на джерела.

Перед передачею перевірте відносні посилання, узгодженість із OpenAPI та відсутність вигаданих полів або endpoint-ів. Для документаційної зміни збірка backend зазвичай не потрібна; якщо змінюється код чи контракт, застосовуйте відповідні [правила перевірки](../../../standards/testing-rules.md).
