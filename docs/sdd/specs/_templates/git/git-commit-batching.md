# Пакетування Git-комітів

Коміт описує один придатний для рев’ю намір і не повинен змішувати не пов’язані зміни.

## Базове правило: розділяйте значну роботу

Не розміщуйте функціональність із кількома незалежними змінами в одному великому коміті. Розділяйте її на невеликі впорядковані коміти, якщо зміни можна окремо рев’ювати, тестувати, скасовувати або cherry-pick-ати.

Типові межі окремого коміту:

- специфікація функціональності або документація;
- доменна модель та інваріанти;
- application-команда/запит і валідація;
- конфігурація persistence або міграція;
- HTTP-контракт/публікація API;
- тести;
- окреме виправлення помилки, зміна лише форматування, згенерований код або оновлення залежності.

Тримайте разом пов’язані міграцію, модель сутності та EF-конфігурацію, якщо поділ залишить репозиторій нездатним зібратися або виконати міграцію. Не діліть роботу лише для створення штучно малих комітів.

## Рекомендовані пакети

1. `docs(<module>): add <feature> specification`
2. `feat(<module>): add domain model and invariants`
3. `feat(<module>): add application use case and validation`
4. `feat(<module>): add infrastructure adapter or migration`
5. `feat(<module>): expose API contract`
6. `test(<module>): cover <feature> scenarios`
7. `docs(<module>): record <feature> verification`

Пропускайте пакет, у якому немає змін. Для малої цілісної зміни поєднуйте сусідні пакети лише тоді, коли їх неможливо рев’ювати незалежно.

## Формат повідомлення коміту

Використовуйте короткий наказовий заголовок:

```text
<type>(<module>): <коротка зміна>
```

Приклади:

```text
feat(catalog): add admin product list query
fix(identity): rotate refresh session on token reuse
docs(sdd): add operations runbook
```

Для значного коміту додайте body після порожнього рядка. Коміт є значним, коли він змінює понад один шар, поведінку API/бази даних/безпеки, має неочевидний компроміс або його не можна зрозуміти лише з заголовка.

```text
feat(identity): add administrator user creation

Create the user through the Identity application use case and assign only
the Admin role. The endpoint is protected by CanManageUsers; passwords and
Identity provider errors are never returned in the response.

Tests: unit tests for validation; API authorization cases.
```

Body пояснює **що змінилося**, **чому це змінилося** та будь-який важливий вплив на сумісність, безпеку, міграцію або перевірку. Він не повинен містити секретів, токенів, connection strings або скопійованих логів.

## Контроль розміру комітів

Дотримуйтеся збалансованого розміру комітів:

- Значну функціональність зазвичай діліть за самостійними намірами, придатними для окремого рев’ю, а не за файлами чи методами.
- Після кожного коміту гілка має збиратися; сам коміт має бути зрозумілим, таким, що його можна окремо протестувати та безпечно скасувати.
- Не створюйте один надто великий коміт, якщо зміни домену, міграції, application-рівня, API та тестів можна перевірити окремо.
- Не перетворюйте одну цілісну велику функціональність на десятки мікрокомітів (наприклад, 20 і більше), якщо їх не можна незалежно переглянути, протестувати чи скасувати.
- Об’єднуйте нерозривні зміни: наприклад, властивість сутності, її EF-конфігурацію та потрібну міграцію. Розділяйте зміни лише там, де є справжня межа відповідальності або поведінки.

Перед створенням комітів опишіть запропоновані пакети змін і коротко поясніть, якщо пакет є незвично великим або малим.

## Правила

- Не поєднуйте форматування, згенеровані файли, оновлення залежностей або не пов’язані виправлення з функціональністю.
- Якщо робота охоплює кілька придатних для рев’ю намірів, створіть кілька комітів замість одного збірного. Упорядкуйте їх так, щоб кожен мав чітку мету, а серію було легко рев’ювати.
- Міграції комітяться разом із відповідною зміною моделі/конфігурації.
- Коміт із несумісною зміною містить `BREAKING CHANGE` у body і посилання на план міграції.
- Фінальний коміт документації фіксує виконані перевірки й відомі обмеження; він не може стверджувати про перевірки, які не запускалися.
