# Product page — огляд і межі

**Модуль:** Catalog  
**Статус:** у роботі  
**Власник:** Catalog  
**Створено:** 2026-07-27

## Мета

Менеджер каталогу створює та розширює товар з українською й російською назвою, slug, типом, фото та категоріями. Дані товару повинні бути достатніми для повного admin frontend, де менеджер може переглянути й налаштувати всі властивості товару.

Для товару типу `Sewing` менеджер обирає операції пошиття, а система показує трудомісткість, повне дробове значення кількості виробів за зміну та три розраховані ціни для кожної вибраної тканини.

## Типи та спільні дані товару

Товар має один тип: `Sewing` або `Ppe`. Для обох типів доступні:

- українська й російська назви;
- slug, який система автоматично генерує з української назви;
- фото, яке можна використати лише після готовності медіафайлу;
- категорії;
- опис, інформаційні блоки та характеристики.

## Загальні правила

- Українська й російська назви обов’язкові, мають до 200 символів і кожна окремо унікальна в межах Catalog. Slug система генерує з української назви через пакет транслітерації, тип — визначений.
- Одна категорія або один медіафайл не додається двічі.
- Якщо товар має фото, головним є щонайменше одне; після видалення головного обирається наступне за порядком.
- `MediaFile`, прив’язаний до Product через фото, не можна видалити, доки це посилання не прибрано з товару. Видалення відхиляється без зміни Product.
- Admin може створювати, переглядати, редагувати та повністю видаляти Product. Видалення Product прибирає його власні деталі й зв’язки, але не видаляє `MediaFile`: файл залишається в Media і може бути використаний повторно.
- Редагування виконується одним повним `PUT` Product: frontend передає всі редаговані спільні та type-specific дані. При зміні `ProductType` старі дані іншого типу видаляються.
- Дані Sewing і PPE взаємовиключні; правила кожного типу описані у відповідних requirement-документах.

## Статус рішень та відкриті питання

### Прийнято

- Sewing-ціна обчислюється на читанні для кожної пари «Product — Fabric»; snapshot і окрема таблиця цін не створюються.
- `piecesPerShift` передається дробовим значенням без округлення.
- Product може мати кілька категорій; однаковий `ProductCategoryId` не додається двічі.
- Sewing Product може мати до двох основних тканин; вони відображаються першими. Для кожного цінового діапазону read-model повертає min/max ціну серед усіх тканин разом з `FabricId`.
- Увесь описовий блок Product локалізований українською та російською: `Description`, `Information` і `Characteristics`.
- `Description` передається як санітизований Markdown, `Information` — як масив блоків «заголовок + plain-text», а `Characteristics` — як масив таблиць із рядками «параметр + значення»; HTML не передається.
- Поточний delivery охоплює лише admin read-model. Він повертає всі налаштовувані дані Product: спільні поля, фото, категорії, описовий блок, Sewing/PPE details, тканини, фурнітуру, операції, показники Sewing і розраховані ціни. Public storefront endpoint винесений за межі поточного delivery.
- Тимчасово всі admin read і write-сценарії Product доступні анонімно. Перед production необхідно окремо погодити й увімкнути authorization policy; поточний anonymous-доступ не є production-рішенням.
- `Idempotency-Key` не використовується в поточному admin delivery: frontend блокує повторне натискання під час запиту, а update виконується за `ProductId`. Якщо з’явиться підтверджена проблема дублювання create-запитів, ключ додається окремою зміною.
- `Slug` не вводиться адміністратором і не надходить у create/update request. Application автоматично генерує його з української назви через пакет транслітерації; БД захищає унікальність slug у межах Catalog унікальним індексом.
- Унікальність української та російської назв гарантується Application і унікальними індексами БД. Тому для slug не застосовуються числові суфікси: він є прямою транслітерацією української назви.
- ID нового Product вводить адміністратор. Він має бути додатним і унікальним у Catalog; повторне створення з тим самим ID відхиляється конфліктом.
- Admin-список Product підтримує єдиний пошук за українською та російською назвами, `Slug` і ID. Текстовий пошук частковий та без урахування регістру, пошук за ID — точний. Також доступна фільтрація за типом товару й однією категорією. Якщо обрана категорія є батьківською, фільтр включає товари з неї та всіх її дочірніх категорій. Дані повертаються сторінками: за замовчуванням 20 товарів, frontend може обрати 10, 20 або 50 товарів на сторінці.
- Admin може сортувати список за ID, назвою, датою створення або датою зміни, у прямому чи зворотному порядку. За замовчуванням список сортується за назвою від А до Я.
- Admin Product API використовує префікс версії `/api/v1`.
- Історія цін і виробничих норм не входить до поточного delivery. Admin read-model завжди показує актуальні `GarmentPartOperation.Min`, ціни тканини/фурнітури та `AdditionalReference.Value`; snapshot/history-таблиці не створюються.
- Усі значення `AdditionalReference` з unit `%` обробляються як відсотки: перед застосуванням у формулі використовується `Value / 100`, а не готовий числовий множник.
- Усі складові зарплати цеху в собівартості Sewing — швея, премія, закрійник, майстер і начальник цеху — розраховуються на один виріб. Місячна `srZpShvei` використовується лише для початкового розрахунку зарплати швеї на одиницю.
- PPE має обов’язкову ручну `BasePrice`; окремі роздрібний і оптовий відсотки з `AdditionalReference` або ручні значення застосовуються до неї.
- `GarmentPartOperation`, `Fabric` і `GarmentAccessory` не можна видалити з Reference, якщо на них посилається хоча б один Product. Видалення відхиляється без зміни Product; події очищення зв’язків не використовуються.
