# Підфаза 03.10 — вузький Reference reader цін для адміністративного списку Product

**Залежить від:** `03.9-admin-list-query-performance.md` і профілювання репрезентативної непорожньої сторінки
**Проєктне рішення:** [admin-list-pricing-reference-reader.md](../../design/admin-list-pricing-reference-reader.md)
**Наступна перевірка:** `../verification/05.3-admin-list-query-performance-verification.md`

- [x] T091 Додати контракт Catalog Application `IProductListPricingReferenceReader` і типи вхідних даних/результатів лише для списку. Контракт приймає тільки унікальні примітивні ID та повертає лише числові поля ціноутворення; він не переносить сутності/DTO Reference до Catalog.
- [x] T092 Реалізувати спеціалізований запит Reference Application та адаптер Host: проєкції за множинами для тканин, фурнітури, операцій і потрібних AdditionalReferences без пошукових запитів інтерфейсу для постачальників/частин одягу; не викликати наявні запити інтерфейсу `GetAll...`.
- [x] T093 Переробити `GetAdminProductsQueryHandler`: після отримання сторінки зібрати множини ID, один раз викликати вузький читач і застосувати наявні формули ціноутворення. Порожні множини ID не мають породжувати запит до бази даних; відповідь списку не змінюється.
- [x] T094 Дослідити наявний механізм інвалідації після запису в Reference. Додати кеш лише якщо він забезпечує задокументований TTL, інвалідацію й семантику для кількох екземплярів; інакше зафіксувати свідоме рішення без кешування.
- [x] T095 Додати модульні/інтеграційні тести: однаковість цін, відсутність пошукових запитів для постачальників/частин одягу, обмежена кількість SQL-команд і відсутність N+1 для розміру сторінки 1/20/50.

## Контрольна точка

Адміністративний список отримує лише потрібні вхідні дані для ціноутворення пакетними запитами. Повний знімок Reference
не викликається обробником списку; кеш, якщо з’явиться, не має неявно або некеровано
повертати застарілі дані.

## Результати реалізації

- Обробник списку більше не викликає повний `IProductReferenceReader.GetSnapshotAsync()`.
  Він збирає унікальні ID з рядків поточної сторінки й викликає один
  `IProductListPricingReferenceReader`.
- Reference `GetPricingReferencesByIdsQuery` має чотири числові проєкції на основі множин:
  fabrics, accessories, operations і AdditionalReferences. Supplier і GarmentPart UI
  пошукові запити не входять до графа залежностей запиту.
- Для порожніх наборів кожен репозиторій Reference не викликається. Ключі ціноутворення Sewing
  передаються тільки коли сторінка містить Sewing Product з тканиною; PPE передає лише
  ID відсотків, що беруться з довідника.
- Кеш не додано: у кодовій базі не знайдено механізму інвалідації або семантики кількох екземплярів для
  записів у Reference, тому кеш із TTL міг би повертати застарілі ціни.
- `ProductAdminListReadModelTests` перевіряє збереження розрахунку мінімальної оптової ціни та один
  виклик читача лише для списку для рядків сторінки. `PricingReferenceQueryHandlerTests` перевіряє лише чотири
  репозиторії цін без пошукових запитів для постачальників/частин одягу.
- `PricingReferenceQueryIntegrationTests` виконується на PostgreSQL: повертає лише запитані
  AdditionalReference і фіксує рівно 4 `SELECT` для ID-set розміром 1, 20 та 50 — кількість SQL
  команд не залежить від кількості товарів на сторінці й не має N+1.
- `dotnet test tests/UnitTests/UnitTests.csproj --no-build` — пройшли 47 тестів;
  `dotnet test tests/IntegrationTests/IntegrationTests.csproj` — пройшли 22 тести.
- `dotnet build src/Bootstrapper/Host.Api/Host.Api.csproj --no-restore -o %TEMP%\\brevierp-03-10-host-build` — успішно, 0 помилок. Ізольований каталог виводу використано, бо запущений локальний Host API блокує звичайний `bin/Debug`.
- Вимірювання наскрізної затримки та порівняння до/після свідомо винесено до
  `05.3-admin-list-query-performance-verification.md`; вони не є частиною цієї реалізаційної підфази.
