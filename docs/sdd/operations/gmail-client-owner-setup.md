# Что получить владельцу для подключения почты BreviERP

Состояние на 2026-11-01: владелец сообщил, что JSON OAuth-клиента ещё нет. Локально ClientId, ClientSecret и RefreshToken в user-secrets и process environment не найдены. Это блокирует реальный контрольный Gmail send, а не разработку ручного результата.

## Действия владельца

1. Открыть [Google Auth Platform → Clients](https://console.cloud.google.com/auth/clients) в согласованном проекте **BreviERP**. Если проект имеет другое имя, выбрать тот, где уже настроены страницы office.brevi.com.ua и OAuth Branding BreviERP. Клиенты калькулятора не менять.
2. Для имеющегося локального помощника нажать **Create client → Desktop app**, назвать клиент **BreviERP — подключение почты** и создать его. Desktop здесь относится к одноразовому локальному получению разрешения; само ERP остаётся веб-приложением. Если уже согласован production Web-клиент, сохранить его настройки отдельно: локальный helper принимает только Desktop JSON и не заменяет Web-клиент автоматически.
3. Сразу нажать **Download JSON** и сохранить файл в личную папку вне Git. Достаточно сообщить программисту путь к файлу; содержимое, Client Secret и токены в чат не копировать. Google рекомендует сохранять секрет при создании клиента. [Управление OAuth clients](https://support.google.com/cloud/answer/15549257?hl=en), [официальный Desktop-путь](https://docs.cloud.google.com/bigquery/docs/authentication/end-user-installed).
4. После проверки файла программист запускает имеющийся helper. Владелец входит в **pp.brevi@gmail.com** и один раз разрешает отправку писем/подтверждение адреса. Запрашиваются gmail.send, openid и email; чтение почты не запрашивается.

Рабочий Google-проект использует In production, как ранее согласовано. Если Branding/Data Access ещё не заполнены, используются уже опубликованные homepage/privacy/terms BreviERP и минимальные scopes из [runbook](crm-gmail-oauth.md). Само подтверждение домена в Search Console не выдаёт приложению токен доступа к ящику.

## Что делает программист после получения файла

Проверяет тип/структуру JSON без вывода секретов, выполняет явный OAuth helper, сохраняет credentials в защищённой конфигурации. Helper сам не отправляет письма и оставляет dispatch выключенным. Затем выполняется отдельно разрешённая контрольная отправка только **wet13prp@gmail.com** от **pp.brevi@gmail.com**: synthetic quote/PDF, одна попытка, реальный результат провайдера и история ERP. Рабочая очередь клиентов не запускается ради проверки. Production secret store и consent подтверждаются по фактическому окружению, а не по наличию страниц сайта.

До получения файла и разрешения аккаунта EN-004 live acceptance остаётся незавершённой. Проверки с подставным HTTP и изолированной БД не заменяют реальную отправку.
